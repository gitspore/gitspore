Layout model

Seven regions. The scene fills the whole page behind the others. Everything else is plain HTML on top.

Three independent settings make every state

The grid areas are calculated from these three settings. We don't draw each state by hand; the rules below decide the tiles.

Rules

  1. Windows tile by count. 1 fills its zone, 2 sit side by side, 3 make two plus one, 4 make two by two. At most 4 windows are visible; a fifth one opens as a tab in the focused tile.
  2. A terminal tile is at least about 650 px wide (80 columns of 13 px monospace). If a new column would make tiles narrower, the window stacks below instead. If there is no room below either, it becomes a tab.
  3. A terminal tile is at least about 350 px tall (about 20 rows). In scene mode the band holds one row of tiles.
  4. Maximise acts on all visible windows. Minimised windows stay minimised.
  5. Focus this = focus mode + minimise every other window.
  6. Entering focus mode closes the side panel. The user can open it again; the windows shrink. Leaving focus mode restores the panel state from before.
  7. Closing a window doesn't stop the agent. It only hides its terminal. Stopping an agent or freeing a pot is a separate action with a confirmation.
  8. Minimised terminals stay alive. Their xterm instance keeps running, and the chip shows the agent's status.
  9. The issue window is a sheet, not a tile. It opens at the top of the main area, over the scene, and closes when the issue is planted or dismissed. It doesn't take part in tiling.
  10. Exactly one window has keyboard focus and shows a strong border. App shortcuts only work while no terminal has focus.

Limits

  • Screen width. Minimum 1280 px. No phone or tablet layout. Below 1280 a message asks for a wider window.
  • Tiles. On a 1440 × 900 laptop: two terminals side by side only with the side panel closed (about 670 px each). With the panel open (about 1050 px left) they stack. At most 4 visible terminal tiles; more become tabs.
  • Pots. One repo, six pots, fixed slots (v3 scope).
  • Camera framing. The view offset can only frame the pots into a rectangle. When the free area is an L-shape, it uses the largest rectangle, so the pots get smaller.
  • Animation. Browsers animate changes of grid column and row sizes, but not of grid-template-areas. Smooth moves between states need the View Transitions API; check the Next.js docs in the repo before relying on it. xterm needs fit() when a transition ends, not on every frame.
  • Keyboard. Esc belongs to the terminal (Claude Code uses it to interrupt). App shortcuts only work when no terminal has focus.
  • Panel backgrounds. backdrop-filter: blur over a WebGL canvas is recalculated every frame. Measure it on our laptops before using it; solid panels are the default.
  • Answer buttons. Depend on spike S3. Until then, answers go through the terminal.
  • Drag from HTML onto the scene. Needs our own drop handling and raycast. It is a should-have; the button path works without it.

Open questions

  1. Issue window placement. A sheet over the top of the main area (as on board frame 7, used here), or a tile in the band like the other windows?
  2. Band width with one terminal. Full width of the main area (used here, simpler framing) or half width as on the board?
  3. Leave-terminal key. Esc is taken by Claude Code. Candidates: Ctrl+`, F6.
  4. Merge. Detect a merge made on GitHub, or offer a merge button in gitspore? The second brings merge conflicts, which are out of scope.
  5. Branch naming. Which name links an agent's branch to its issue (GSP-<n>_…, issue-<n>-…)?
  6. Seed mark. Chosen from the issue number (8 symbols) or from GitHub labels?
  7. v3 adoption. The ticket mapping assumes the team adopts v3. Until then, #12 and #13 stay as they are.
